## Connection Pooling with PgBouncer

PostgreSQL uses a process-per-connection model. Spawning thousands of connections consumes heavy RAM and CPU context-switching overhead. **Connection pooling** is critical for high-concurrency applications.

### Why PgBouncer?
PgBouncer is a lightweight connection pooler for PostgreSQL. Instead of your app opening 1,000 direct connections to Postgres, your app opens 1,000 connections to PgBouncer, which multiplexes them over a small pool of (e.g., 50) actual PostgreSQL connections.

### Pooling Modes
1. **Session Pooling:** A server connection is assigned to a client for the entire duration of their session. (Good for legacy apps, low connection reuse).
2. **Transaction Pooling (Recommended):** A server connection is assigned to a client only during a transaction. Once `COMMIT` or `ROLLBACK` is issued, the connection returns to the pool. Ideal for serverless or high-throughput web apps.
3. **Statement Pooling:** Multi-statement transactions are not allowed. Connection is returned after every single statement.

### PgBouncer Configuration (`pgbouncer.ini`)

```ini
[databases]
# Map virtual db to actual db
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
listen_port = 6543
listen_addr = *
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt

# Crucial settings
pool_mode = transaction
max_client_conn = 10000       # Max connections from apps to PgBouncer
default_pool_size = 50        # Max connections from PgBouncer to PostgreSQL
min_pool_size = 10
reserve_pool_size = 10
server_idle_timeout = 600
```

> **Cloud Note:** Managed services like AWS RDS Proxy and Supabase provide built-in connection poolers based on PgBouncer.

## EXPLAIN and Query Execution Plans

The `EXPLAIN` command shows the execution plan generated by the PostgreSQL planner.

```sql
-- Basic plan (Estimated costs)
EXPLAIN SELECT * FROM employees WHERE department_id = 1;

-- Actual execution (Runs the query and compares estimates to actuals)
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM employees WHERE department_id = 1;

-- Verbose JSON output (Great for external visualization tools like PEV2)
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT JSON)
SELECT e.*, d.name FROM employees e JOIN departments d ON e.department_id = d.id;
```

### Reading EXPLAIN Outputs

| Node Type | Description | When to Worry / How to Fix |
|-----------|-------------|----------------------------|
| **Seq Scan** | Reads entire table sequentially | Bad on large tables. Add an index or refine `WHERE`. |
| **Index Scan** | Reads index to find pointers, then fetches rows from table | Normal. Can be slow if fetching many scattered rows. |
| **Index Only Scan** | Satisfies query using ONLY the index | **Best case.** Requires covering indexes (`INCLUDE`). |
| **Bitmap Index Scan** | Builds a bitmap of row locations, then fetches | Good for moderate selectivity, groups disk reads. |
| **Nested Loop** | For each row in outer table, scans inner table | Bad if outer result set is large. |
| **Hash Join** | Builds hash table in memory, probes it | Good for large unsorted datasets. Increase `work_mem` if hashing spills to disk. |
| **Merge Join** | Sorts both sets, merges them | Fast, but requires pre-sorted data or an index. |
| **Sort** | Sorts rows in memory or disk | Watch for "Sort Method: external merge Disk". Increase `work_mem`. |

## Configuration Tuning (`postgresql.conf`)

Tuning hardware utilization is key to maximizing PostgreSQL performance.

### Memory Tuning

```conf
# Shared memory buffers (RAM used for caching data)
shared_buffers = 2GB                # Generally 25% of total system RAM
# Planner hint for how much cache is available in the OS
effective_cache_size = 6GB          # Generally 75% of total system RAM

# Memory for sorting and hashing per operation (NOT global limit)
# If a query has 2 sorts, it can use 2x work_mem. Keep it moderate.
work_mem = 16MB                     
# Memory for VACUUM, CREATE INDEX, ALTER TABLE
maintenance_work_mem = 512MB        
```

### Storage and I/O Tuning

```conf
# Cost of random vs sequential fetch. 
# Defaults (4.0/1.0) favor HDDs. For modern NVMe SSDs, lower random_page_cost.
random_page_cost = 1.1              # 1.1 for SSDs, 1.0 for ultra-fast NVMe
seq_page_cost = 1.0

# Number of concurrent I/O requests
effective_io_concurrency = 200      # 200 for SSDs, 0 for HDDs
```

### Parallel Query Operations

```conf
# Enable parallel execution for large analytical queries
max_parallel_workers_per_gather = 4
max_parallel_workers = 8
max_parallel_maintenance_workers = 4 # Speeds up B-Tree index creation
```

## Vacuum, Bloat, and Freezing

PostgreSQL uses MVCC (Multi-Version Concurrency Control). When you `UPDATE` or `DELETE`, the old row (tuple) is kept until all active transactions no longer need it. These "dead tuples" cause **Table Bloat**.

### Autovacuum
Autovacuum cleans up dead tuples. **Never turn autovacuum off.** Instead, tune it to run more frequently and aggressively.

```conf
autovacuum_vacuum_scale_factor = 0.05  # Vacuum when 5% of table changes (default 0.2 is too high)
autovacuum_analyze_scale_factor = 0.02
autovacuum_vacuum_cost_limit = 2000    # Make vacuum run faster (default 200 is too slow)
```

### Manual Maintenance

```sql
-- Update statistics (helps query planner)
ANALYZE employees;

-- Standard vacuum (reclaims space for reuse, does NOT shrink file size)
VACUUM ANALYZE employees;

-- Full vacuum (WARNING: Takes an EXCLUSIVE LOCK and rewrites entire table)
-- Use pg_repack extension instead for production environments
VACUUM FULL employees;
```

## Advanced Query Optimization Patterns

### 1. Covering Indexes
Avoid heap lookups entirely by including frequently selected columns in the index payload.
```sql
CREATE INDEX idx_users_email ON users(email) INCLUDE (first_name, last_name);
-- SELECT first_name FROM users WHERE email = 'x' will be an Index Only Scan
```

### 2. Partial Indexes
Index only a subset of data to save disk space and speed up specific queries.
```sql
CREATE INDEX idx_active_users ON users(last_login) WHERE status = 'active';
```

### 3. Keyset Pagination (Seek Pagination)
`OFFSET` is slow for deep pages because the database must compute and discard the skipped rows.
```sql
-- BAD (OFFSET scales O(N))
SELECT * FROM events ORDER BY created_at DESC OFFSET 100000 LIMIT 10;

-- GOOD (Keyset pagination uses index to jump directly to the row)
SELECT * FROM events WHERE created_at < '2023-01-01' ORDER BY created_at DESC LIMIT 10;
```
