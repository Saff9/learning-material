# 22 - AI & Vector Workloads

> Comprehensive Guide to Vector Search, pgvector, embeddings, Indexing, and RAG architectures.

PostgreSQL has become a leading database for AI applications due to the `pgvector` extension. It allows you to store, index, and query vector embeddings alongside your traditional relational data.

---

## Core Concepts

1. **Embeddings:** High-dimensional arrays of floating-point numbers generated by AI models (like OpenAI's `text-embedding-ada-002` or `text-embedding-3-small`). They represent the semantic meaning of text, images, or audio.
2. **Vector Search:** Finding the "nearest neighbors" to a query vector in a high-dimensional space.
3. **Similarity/Distance:** Measured via Cosine Similarity, L2 (Euclidean) Distance, or Inner Product.

---

## 1. Setting up pgvector

```sql
-- Install the extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Create a table combining metadata and vectors
CREATE TABLE kb_articles (
    id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    category VARCHAR(50),
    created_at TIMESTAMPTZ DEFAULT NOW(),
    -- The size of the vector depends on your AI model (e.g., OpenAI is 1536)
    embedding VECTOR(1536)
);

-- Inserting an embedding (typically done via your application code using pg/psycopg)
INSERT INTO kb_articles (title, content, category, embedding)
VALUES (
    'How to reset password', 
    'Go to settings and click reset...', 
    'support', 
    '[0.015, -0.022, 0.009, ... ]' -- 1536 floats
);
```

## 2. Distance Operators and Querying

`pgvector` provides operators for calculating distance between vectors. To find the "most similar" items, you order by distance ascending.

```sql
-- 1. Cosine Distance (<=>) - Most common for OpenAI embeddings
SELECT id, title, 1 - (embedding <=> '[query_vector]') AS similarity_score
FROM kb_articles 
ORDER BY embedding <=> '[query_vector]' 
LIMIT 5;

-- 2. L2 (Euclidean) Distance (<->)
SELECT title FROM kb_articles ORDER BY embedding <-> '[query_vector]' LIMIT 5;

-- 3. Inner Product (<#>)
SELECT title FROM kb_articles ORDER BY embedding <#> '[query_vector]' LIMIT 5;
```

## 3. Vector Indexing Strategies

Without an index, vector search requires an **Exact Nearest Neighbor (KNN)** search—comparing the query against every row in the table (Sequential Scan). This is slow. 
Indexes provide **Approximate Nearest Neighbor (ANN)** search, sacrificing a tiny bit of accuracy for massive speed.

### HNSW (Hierarchical Navigable Small World) - Recommended
HNSW builds a multi-layered graph. It is the best default choice: fast query times, high recall, and handles updates well.

```sql
-- Create an HNSW index using cosine distance
-- m: max number of connections per layer (16-64)
-- ef_construction: size of dynamic candidate list during build (64-128)
CREATE INDEX idx_kb_embedding_hnsw ON kb_articles 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Querying with HNSW (Tuning search accuracy vs speed)
SET hnsw.ef_search = 100; -- Higher means better accuracy, slightly slower
SELECT title FROM kb_articles ORDER BY embedding <=> '[query_vector]' LIMIT 5;
```

### IVFFlat (Inverted File Flat)
IVFFlat divides the vector space into clusters (lists). Faster to build and uses less memory than HNSW, but queries are slower and you MUST build the index *after* inserting data.

```sql
CREATE INDEX idx_kb_embedding_ivf ON kb_articles 
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100); -- roughly (rows / 1000)
```

## 4. RAG Architecture (Retrieval-Augmented Generation)

RAG provides an LLM with external context to reduce hallucinations. PostgreSQL excels here because you can combine Vector Search with traditional SQL filters (Hybrid Search).

### Architecture Flow:
1. **Chunking:** App splits a large PDF into 500-word chunks.
2. **Embedding:** App calls OpenAI to vectorize each chunk.
3. **Storage:** Stored in Postgres `document_chunks` table.
4. **Querying:** User asks a question. Question is vectorized.
5. **Retrieval:** Postgres retrieves top 5 most similar chunks (filtered by user access rights).
6. **Generation:** App sends prompt to LLM: "Using this context: [chunks], answer: [question]".

### Hybrid Search Implementation (Vector + Relational Filter)

Combining semantic search with metadata filtering is where Postgres beats dedicated vector databases.

```sql
-- Get semantic matches, but ONLY for articles the user has access to (tenant isolation)
-- and only updated in the last year.
SELECT id, title, content
FROM kb_articles
WHERE tenant_id = 123 
  AND category = 'engineering'
  AND created_at > NOW() - INTERVAL '1 year'
ORDER BY embedding <=> '[query_vector]'
LIMIT 5;
```

### Advanced Hybrid Search (Vector + Full-Text Search)

Sometimes keyword search is better than semantic search (e.g., searching for exact product IDs or names). We can combine `pgvector` with PostgreSQL's `tsvector`.

```sql
-- Use Reciprocal Rank Fusion (RRF) or weighted scoring
WITH semantic_search AS (
    SELECT id, 1 - (embedding <=> '[query_vector]') AS v_score
    FROM kb_articles ORDER BY embedding <=> '[query_vector]' LIMIT 50
),
keyword_search AS (
    SELECT id, ts_rank(to_tsvector('english', content), plainto_tsquery('english', 'search terms')) AS t_score
    FROM kb_articles
    WHERE to_tsvector('english', content) @@ plainto_tsquery('english', 'search terms')
)
SELECT 
    k.title,
    COALESCE(s.v_score, 0) * 0.7 + COALESCE(k.t_score, 0) * 0.3 AS hybrid_score
FROM kb_articles k
LEFT JOIN semantic_search s ON k.id = s.id
LEFT JOIN keyword_search k_idx ON k.id = k_idx.id
WHERE s.id IS NOT NULL OR k_idx.id IS NOT NULL
ORDER BY hybrid_score DESC
LIMIT 5;
```

## 5. Scaling Vectors (Memory Optimization)

Vector indexes consume significant RAM. High-dimensional embeddings (1536) for millions of rows can exceed memory limits.

### Half-Precision Vectors (pgvector 0.8+)
Stores vectors using 16-bit floats instead of 32-bit floats. Cuts memory usage by 50% with negligible impact on accuracy.

```sql
-- Requires altering the column to use the halfvec type
CREATE TABLE articles_half (
    id SERIAL,
    embedding halfvec(1536)
);

CREATE INDEX idx_half ON articles_half USING hnsw (embedding halfvec_cosine_ops);
```

### pgvectorscale
An extension built on top of pgvector (developed by Timescale) that introduces **StreamingDiskANN**. It allows vector indexes to live on SSDs rather than requiring them to fit entirely in RAM, enabling billion-scale vector search in Postgres.
